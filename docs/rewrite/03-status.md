### Completeness critic, round 2

Verdict: The design covers every deliverable of the brief (screens, data model, 40-lesson curriculum, numeric pacing model, module list and build entry, frozen interfaces, work packages, milestones, a risk-by-risk retirement table) and closes 26 of the map's 29 gaps knowingly. Its code citations are accurate where checked. Two high issues remain: the Node checker's central check (a stop that no step visits, the --json visit labels, the --pace leg lengths) needs board3d.js internals that the specified Node loader never loads, so the mechanism that retires risks E and 10 is unspecified; and the browser-side dry pass at load() runs folds synchronously with no bound, contradicting 7.3, while the fixed beat count it produces is not guaranteed to survive a wait beat's key timing or an unfinished fold at play time. Seven medium issues (a non-deterministic RTC lesson, the repeat/times off-by-one, Explore's Play across instructions, the Lesson ring's stepMs source, missing per-lesson terms/minutes and the term list, a double screen beat in compile, an unlisted program appendix) and a dozen low ones are listed with concrete fixes. With the two high items resolved the spec is implementable in parallel as written.

So the check that retires risks E and 10 at M1 and the writers' main artifact are unspecified. (`tools/ids.mjs` lists what a trace model *can* emit per model, not what a given step *does* visit.)
  Fix: Add to 7.7 one of: (a) load `src/vendor/three.module.min.js` (as `THREE`) and `src/ui/board3d.js` into the Node context with a `document` stub (`injectStyle` runs only in the constructor, so parse needs `THREE`, `THEME`, `clamp`), and give `LearnPlan` a pure `visits(step, model, machine) → [{ part, label }]` that reimplements `trJourney`'s dispatch table (map §4.3: inside → `CPU_TRACE.inside(ctx)`, bus by phase → `cm.out/status/in/write` + `GLUE` + the device model, cache → `CACHE_CARD*`, page → `PAGE_CARD`, btb → `P5_CARDS`, irq → `PIC_IRQ_TRACE`, …) over `BoardKit` with `ctx = { I, s, ev, m: machine, e, part }` and `BoardKit.BLK_*` for the remap; assert its output against `bd.trJourney(s).segs` for every step of the letter program in `learn-smoke.mjs` so the two cannot drift; or (b) move check (4)'s visit half, the `--json` visit labels and `--pace` legs to the Chrome checker (`bd.trJourney(s)` on the real board) and have the Node checker validate keys only against `LEARN_UNITS`. - **[high] 7.5 The dry pass · 3.2 semantics of `run`/`wait` · 5.3 (`foldWallMs`) · 7.3 `runToSync` · decision 25**
  Problem: Three contradictions around the dry pass that fixes n. (1) 7.5 says `load()` runs `run` folds with `runToSync`, while 7.3 says `runToSync` 'exists for Node (the checker) only' because a long run on the P6 JS core 'would block the page for seconds'; the dry pass runs in the browser and its folds have no clock bound at all (only `from` has the 4 M-clock cap), so 80686-05's run to the printed clocks or 80386-04's run to the end can block the page well beyond the claimed 'tens of milliseconds'. (2) At play time a `run` beat stops at `foldWallMs` and 'offers keep running'; if the learner presses Next instead, the machine is not where the dry pass left it, so later beats' selectors, templates and `{clocks}` diverge from the compiled beats. (3) In 8086-08 the dry pass types the key instantly, but at play the key arrives at an arbitrary clock; the timer interrupts that land in the following `step: { count: 8 }` and runs fall elsewhere, so the aside beats (which 7.5 rule 4 inserts as beats) can differ from the dry pass and n changes, against principle 4 and the Chrome assertion 'n equals the fixture's beats.length'.
  Fix: (1) Make the dry pass async and sliced like `runTo` (it already awaits `runTo(from)`): folds run through `startFF`/`ffFrame` slices under the 'Running to the lesson's start…' card; add a per-lesson dry-pass budget (`LN_PACE.dryPassClocks`, e.g. 4 M) that the checker prints per lesson and fails above, as check (3) does for `from`. (2) Define: Next on an unfinished fold finishes the fold first (the caption keeps 'Running…' until `ffEnd`), or the fold's remainder runs synchronously up to the same budget; the learner never advances past an unfinished `run`. (3) Make the aside an overlay state of the beat that hosts it (a second caption shown for `readH`, then the beat continues), never a separate compiled beat, so n is fixed by the writer's beats plus the deterministic fold splits; or, if asides stay beats, state that lessons with a `wait` beat count asides from the dry pass and any extra one at play time is folded silently. Update decision 25 and the fixture description (interface 12) to match.

- **[medium] 3.2 `repeat` · 4.1 lesson 8086-05-jumps · 4.5 lesson 80586-03-btb**
  Problem: `repeat: { times: 4, then: 'skip' }` is defined as 'run the next `times` executions of the same text silently'. The five-stars loop executes `jnz` five times (four taken, one fall-through, measured in section 0). The first execution is traced, so `times: 4` silences executions 2-5, including the fall-through that the outline says is traced ('the fall-through JNZ (one step; traced…)'), and the parenthetical of `then: 'skip'` also promises 'the fall-through is traced'. Either `times` counts taken passes only (then the definition is wrong) or the lesson needs `times: 3`. The same ambiguity hits 80586-03 (`repeat: { times: 2 }` between the second JNZ and the fall-through).
  Fix: Define `times` as the number of further *taken* executions to fold ('the next `times` executions that jump back'), and state that with `then: 'skip'` the first execution whose outcome differs from the folded ones (the fall-through) is always traced; or keep the definition and change 8086-05 to `times: 3` and 80586-03 to `times: 1`. Have the checker print, per `repeat`, how many executions it folded and whether the next traced one was the fall-through.
